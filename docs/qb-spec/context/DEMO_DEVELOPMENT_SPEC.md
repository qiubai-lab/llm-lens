# 新演示开发流程

本规范由用户明确要求建立，适用于新增演示主题，以及改变已有演示核心知识解释的扩展。技术文档先于演示实现；已有技术事实源优先维护，不重复创建。

## 事实源与交付位置

- 主题技术文档：`docs/demos/<topic>/TECHNICAL_DESIGN.md`。
- 起草模板：[技术文档模板](../../demos/_TEMPLATE.md)。协议、样例较多时可拆为同目录附录，并由主文档链接。
- 长期工程规则留在本文件及 [工程规范](ENGINEERING_STYLE_SPEC.md)；任务规格与验收证据沿用 `docs/qb-spec/`。
- 技术文档记录“讲什么、依据什么、如何演示”；源码实现这些契约，不能自行改写领域事实。

## 必须遵守的顺序

1. **确定教学问题**：说明受众、前置知识、完成后能理解什么、首版范围和不包含什么。
2. **调研技术事实**：优先官方文档、标准或原始论文；实际打开来源，记录 URL、核对日期、版本/适用范围。不能把搜索摘要当作证据。记录会影响演示的限制与尚未解决的问题。
3. **先落地技术文档**：写清概念、输入/输出结构、正常流程、结束与异常边界；提供可复核样例。区分官方事实、项目设计决策、教学简化和待确认事项。预设数据及统计值明确标记为示意。
4. **再设计演示**：在同一文档补充逐幕学习目标、状态与动画映射、交互、框架复用、可访问性、模块边界和验收标准。动画不得暗示文档未建立的能力或真实内部过程。
5. **通过编码前检查后实现**：实现计划或任务规格链接技术文档。核心规则与视图分离，沿用现有外壳、语义变量和 [UI 设计规范](UI_STYLE_SPEC.md)。实现中发现事实变化，先更新技术文档，再改行为。
6. **核对文档与实现并交付**：检查样例、最终状态和动画说明一致；执行适用的工程及浏览器验证，记录证据。文档与相关实现一起提交，维护来源核对记录。

这里的检查是开发者必须完成的自检，不新增用户批准环节。用户已授权实现时，完成检查后继续实现；用户仅要求调研或规划时，只交付文档。不得将“文档完成”写成“演示已经实现”。

## 编码前检查：缺项不得开始演示实现

- [ ] 教学目标、前置知识、首版范围明确。
- [ ] 影响教学正确性的事实有已读取的权威来源和核对日期。
- [ ] 关键输入、输出、状态转换及结束条件有样例或明确契约。
- [ ] 教学简化、模拟/回放/真实执行边界有标注。
- [ ] 不存在影响核心行为的未解决问题；非阻塞问题有明确延期范围。
- [ ] 每幕有学习目标、动画含义及必要交互，技术事实能对应到画面。
- [ ] 模块职责、共享框架复用与验收标准可执行。

不得用“待补充”占位满足检查。只调整字号、对齐、颜色或不改变知识解释的动效时，不需要新建技术文档；仍遵循 UI 与工程验证规范。

## 维护与验证

- 新主题开始实现前重新核对容易变化的接口事实；协议支持范围变化时同步更新来源、样例、解析和演示说明。
- 历史归档是追溯材料，不自动成为当前接口事实源。既有演示不要求一次性补齐全部文档，修改其核心教学内容时按本流程补齐受影响范围。
- 领域或协议转换用有意义的测试保护；前端用 BetterWright 验证相关场景、窄屏、键盘和减少动态效果。截图需实际查看。
- 文档变更检查本地链接、示例语法、状态语义及事实/设计区分；仅文档变更不需要运行页面动画或新增业务测试。
- 这是项目级开发和审查约束；当前未增加自动 CI 门禁。不能声称 CI 已验证文档存在或来源正确。
